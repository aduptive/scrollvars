Same workload, three engines — same frames, 15× less JavaScript

Scroll-scrubbed elements (translate + opacity), scroll driven top→bottom→top over 12 s — three passes: 150 elements, 900, and 900 with 12 ms of synthetic "app work" burned per frame — the headroom test. Frame delivery is flat until the main thread saturates, so on fast machines every engine shows 60 fps; the last pass adds synthetic app work to probe headroom. On capable hardware all three engines deliver the same frames — that is the finding: the 46 KB engines buy no extra performance here, they buy API surface. The differences that persist are the bundle column, no-JS/SSR behavior, and cost on weak devices (to simulate one: DevTools → Performance → CPU 6× slowdown, then run again). Lighthouse mobile (Moto G emulation, the PageSpeed profile) on the same pages, load-only: scrollvars 100 · framer-motion 94 (LCP 2.8 s) · GSAP+ST 88 (TBT 230 ms — building 900 triggers blocks the throttled main thread). Engine bytes and per-element setup are exactly what PageSpeed's metrics punish.

Same frames at 2.2× less CPU and 8× less memory than framer-motion — on phones that is battery and headroom for your own code. GSAP is genuinely efficient; against it the difference is the 15× bundle, the heap, and the no-JS/SSR story.

Methodology: identical DOM and scroll driver in every page; the only variable is the animation engine. Bundle sizes measured from jsDelivr/esm.sh (framer-motion additionally needs React, not counted). Run it on your own machine — that's the point. Sources: scrollvars · gsap · framer-motion
